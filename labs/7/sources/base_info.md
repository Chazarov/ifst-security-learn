# CSRF (Cross-Site Request Forgery) 
по-русски называют межсайтовой подделкой запроса. Суть не в краже пароля с клавиатуры и не во взломе шифрования, а в том, что браузер жертвы сам отправляет на доверенный сайт запрос, который жертва не собиралась выполнять осознанно. Сайт видит привычную сессионную cookie, считает пользователя авторизованным и выполняет действие: смена пароля, перевод денег, смена email, удаление записи. Атакующая страница при этом открыта на другом URL или под видом «похожего» интерфейса.

Механизм держится на том, как браузер устроен по умолчанию. После входа bWAPP выдаёт cookie (часто PHPSESSID). Пока сессия жива, любой запрос с того же браузера на тот же хост localhost:8080 обычно уходит вместе с этой cookie автоматически. Политика same-origin не запрещает сайту A отправить форму или картинку на сайт B: запрос создаёт браузер жертвы, а не JavaScript «от имени A с доступом к cookie B» в смысле чтения — но для CSRF чтение cookie не нужно, нужно только чтобы сервер B получил cookie при изменяющем запросе. Отсюда классические векторы: скрытая форма с method GET или POST и action на жертвный URL, тег img с src равным URL смены пароля, автосабмит через onload, iframe target. Пользователь может даже не видеть перехода на bWAPP, если запрос ушёл в скрытый iframe.

Уязвимость на стороне приложения: нет непредсказуемого CSRF-токена в форме, опасные операции допускаются по GET, сервер не проверяет заголовки Origin и Referer, cookie без SameSite=Strict или Lax. Токен синхронизатора — случайное значение в сессии и в скрытом поле формы; сервер при смене пароля сравнивает их. Без знания токена чужая страница не может собрать валидный запрос, даже если cookie у жертвы есть. SameSite=Lax режет отправку cookie при cross-site POST с чужих сайтов; Strict ещё жёстче. Это не заменяет токен полностью, но сужает окно. Re-authentication — повторный ввод текущего пароля перед сменой — усложняет сценарий «один клик по ссылке».

CSRF путают с фишингом. Фишинг — поддельная страница входа, пользователь сам вводит логин и пароль, данные уходят атакующему. CSRF — жертва уже залогинена, пароль для атаки не обязателен: достаточно cookie. Поддельная страница входа в лаборатории — социальная оболочка: человек думает, что «вылетел» и снова логинится, а в фоне уходит запрос смены пароля на настоящий bWAPP по ещё живой сессии в другой вкладке или в той же, если cookie не истекла. Введённые в фейковую форму логин и пароль на CSRF не опираются: сервер bWAPP при csrf_1.php смотрит на сессию, а не на то, что напечатали на чужом HTML. Если сессии нет, смена пароля не сработает — это важная мелочь для воспроизведения.

В этой лаборатории используется смена пароля через POST на password_change.php: поля password_curr, password_new, password_conf, action=change. Браузер жертвы прикрепляет PHPSESSID; сервер не проверяет CSRF-токен. Атакующая страница (resolve/csrf_attack/basic.html или index.html) содержит скрытую form method=POST target=iframe, по клику отправляет новый пароль. Текущий пароль в форме должен совпадать с реальным (по умолчанию bug для bee). Защита: CSRF-токен, SameSite, проверка Origin/Referer, повторная аутентификация перед сменой пароля.
